We've [recently discussed]({{< relref "git-object-storage" >}}) how `git` generally stores things as `Git` objects.

In this post, we'll dive into the specifics of hot it stores `Blob` objects.

<!--more-->

## Git objects database

Whenever you track a file with 'git', it places is it in the `objects` database, which is a directory you can find
under the following path `.git/objects`.

Furthermore, `git` is a `content-addressable filesystem`, which means that `git` acts as some sort of key-value store, where the key
is generated by git based on the actual content of the file.

The keys are basically [SHA-1](https://en.wikipedia.org/wiki/SHA-1) hashes of the content being stored.

## When does git create these "keys" and "values"

I actually learned that git saves the files in its database the moment you a `git add`, and not when you run `git commit`.

Say you want to save a file called `name.txt` at the root of your repository, whose content is simply the string `Amrou`.

```bash

echo "Amrou" >> name.txt
git add name.txt
git status
```

This will result in the following output

<pre><code>On branch main
Changes to be committed:

<span style="color: green;">  new file:   name.txt</span>
</code></pre>

What that means is, git has already saved that file for you in the `objects` directory.

So if you run `ls .git/objects`, you should be able to see a folder named `b3`, inside of which there's a binary file
called `b814480933d6b4e0a955fd39bb0b75e6719c84`

The reason I know these hash values in advance is that given the exact same content, `git` will always generate the same hash.
It's the founding principal of hashing functions.

## The general object file structure

Once you've "added" a file, `git` stores it in binary format, but it does so following a specific structure that it can easily parse later.

Each file is divided into several blocks:
![Raw structure](../raw-object-structure.png)

Let's dive a bit deeper into the detail of each of these blocks:

* `object_type`: The type of the object being stored, e.g. a `blob`, a `tree`, a `commit`, etc.
* `ascii_space`: A delimiter that when git reaches, it knows it has finished reading the `object_type` block. It's basically the `0x20` hex.
* `object_size`: The size of the content being saved, represented as an ASCII decimal
* `null_byte`: A delimiter that when git reaches, it knows it has finished reading the `object_size` block.
* `object_content`: The binary representation of the actual content that git is saving, of size `object_size`

## How `git` reads a git object file

Let's build on top of the previously given example: Storing the string `Amrou` in `name.txt`.

> Note: Git compresses the contents of the `name.txt` file before it dumps in that path, so the following example is the decompressed content

Like we said, that would've created a file under the path `.git/objects/b3/b814480933d6b4e0a955fd39bb0b75e6719c84`.

Now, if we look inside that file, we'll find the following byte-content:

```bin
62 6c 6f 62 20 35 00 41 6d 72 6f 75
```

1. Git starts reading until it hits the `space` byte, non-inclusive, so that's `62 6c 6f 62` which when converted to an `ASCII` string it becomes: `blob`.
2. Git moves past the `space` byte, and starts reading until it hits the `null separator` byte, non-inclusive as well. So that's: `35`, which is `ASCII` code for the decimal `5`, meaning the file has only 5 bytes.
3. At this point, `git` as all the metadata, so it moves past that `null separator` byte and reads until the end, which is the content of the file: `41 6d 72 6f 75`.

If you convert `41 6d 72 6f 75` from hex to ASCII string, you'll get: `Amrou`.
